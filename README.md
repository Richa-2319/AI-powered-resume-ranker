# Redrob AI Candidate Ranker

AI-powered candidate ranking system built for the Redrob India Runs Data & AI
Challenge. Ranks 100,000 candidate profiles against a Senior AI Engineer job
description — not by keyword matching, but by understanding career history,
skill depth, behavioral signals, and platform activity the way a strong
recruiter would.

## Why two notebooks

The challenge's compute constraints require the **ranking step** that
produces `submission.csv` to run in **≤5 minutes, CPU-only, with no network
access** (no GPU, no hosted LLM/embedding API calls). Generating semantic
embeddings for 100K candidates does not fit that budget — so the pipeline is
split:

| Notebook | Time budget | What it does |
|---|---|---|
| `notebooks/00_eda.ipynb` | n/a | Exploratory analysis that drove every scoring decision below |
| `notebooks/PRECOMPUTE_notebook.ipynb` | **No limit** — run once, offline | Loads all candidates, extracts structured features, embeds every profile + the JD, saves everything to `artifacts/` |
| `notebooks/RANK_notebook.ipynb` | **≤5 min, CPU-only, no network** | Loads only the small precomputed artifact files, computes cosine similarity (vectorised numpy), scores, and writes `submission.csv` |

`RANK_notebook.ipynb` never reads the raw `candidates.jsonl` file — every
field it needs (title, company, skills summary, behavioral signals) is
already baked into `artifacts/features.parquet` during precompute. This is
what keeps the ranking step's wall-clock time low and independent of disk
speed or file layout in the grading sandbox.

## How to reproduce

### Step 1 — Precompute (run once, no time limit)

```bash
jupyter nbconvert --to notebook --execute notebooks/PRECOMPUTE_notebook.ipynb
```

Or open it in Jupyter and run all cells. This:
- Loads all 100,000 candidates
- Extracts six structured sub-scores per candidate (title, career, skill,
  experience, location, education), plus a honeypot-penalty multiplier and
  an availability multiplier
- Builds a text document per candidate and embeds it (and the JD) using a
  local `sentence-transformers` model (`all-MiniLM-L6-v2`) — no API calls
- Saves all of the above, including every field needed later for reasoning
  text, to `artifacts/`

This is the slow step (~45–90 minutes on CPU for the embedding pass) and is
**not** subject to the 5-minute budget.

### Step 2 — Rank (the timed, graded step)

```bash
jupyter nbconvert --to notebook --execute notebooks/RANK_notebook.ipynb
```

This:
- Loads the four small files from `artifacts/` (a few seconds)
- Computes cosine similarity between every candidate embedding and the JD
  embedding via one vectorised numpy matrix multiply
- Combines structured score (75%) with semantic similarity (25%), then
  applies the honeypot and availability multipliers
- Validates the top 100 (no honeypots, scores non-increasing, no duplicate
  IDs) and writes `submission.csv`
- Prints the actual wall-clock time taken, so you can confirm the ≤5-minute
  budget is met on your machine before submitting

### Step 3 — Validate format

```bash
python validate_submission.py submission.csv
```

## Scoring methodology

Six structured components (weighted, sum to 1.0) combined with two
multiplicative penalties/boosts:

| Component | Weight | Signal |
|---|---|---|
| Career quality | 30% | Time spent in AI/ML-relevant roles at product companies; job-tenure stability; penalises pure-consulting backgrounds (TCS/Infosys/Wipro/etc.) |
| Title relevance | 25% | Current + historical titles matched against an AI/ML/Search/Retrieval taxonomy vs. an explicitly off-domain taxonomy |
| Skill depth | 25% | Core AI/ML skills (embeddings, vector search, retrieval, ranking, fine-tuning, etc.) weighted by proficiency level × duration × endorsements; penalises keyword-stuffing skills |
| Experience fit | 10% | Years of experience scored against the JD's 5–9 year sweet spot |
| Location fit | 5% | Preferred India hub cities, with partial credit for relocation willingness |
| Education | 5% | Institution tier + relevance of field of study |

Then:

- **Honeypot multiplier** (0.0–1.0) — flags and penalises profiles with
  internally inconsistent data (e.g. stated years of experience far
  exceeding summed career-history duration, implausible counts of "expert"
  -rated skills, contradictory behavioral signals). A multiplier of 0.0
  removes the candidate from contention entirely.
- **Availability multiplier** (0.20–1.0) — recency of activity, open-to-work
  flag, recruiter response rate, interview completion rate, notice period,
  and GitHub activity, combined into one factor so an excellent-on-paper but
  unreachable/inactive candidate is not ranked above a slightly-less-perfect
  but actually hireable one.

All weights and thresholds (e.g. what counts as a "long" notice period, how
to treat the dataset's `-1` sentinel values for missing GitHub/offer-rate
data) were derived empirically from `00_eda.ipynb`, not assumed from the job
description alone — see that notebook for the underlying distributions.

## Reasoning column

Each of the 100 rows in `submission.csv` includes a short, data-grounded
reasoning string built entirely from precomputed fields (title, company,
years of experience, top matched AI skills, location, response rate, GitHub
score, and any honeypot/availability warnings). No LLM is called to generate
this text — it is template-built from the same numbers used for scoring, so
it can't hallucinate facts not present in the candidate's profile.

## Compute constraint compliance

`RANK_notebook.ipynb` Cell 7 prints the measured wall-clock time for the
full ranking run and explicitly checks it against the 300-second budget. The
notebook makes no network calls and no GPU calls — embeddings are loaded
from disk (already computed) and similarity is a single CPU numpy operation.
